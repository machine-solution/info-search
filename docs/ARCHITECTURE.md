# Архитектура Wikisearch

## Цели

Текущая версия — самостоятельный корпусно-независимый текстовый поисковик.
Архитектура должна позволить последовательно добавить
словопозиции, BM25, L2-модель и гибридный retrieval, не переписывая ingestion и
хранилище документов с нуля.

Основные ограничения:

- C++20 в index-time и query-time;
- ограниченная и предсказуемая RAM;
- отсутствие внешнего поискового движка;
- воспроизводимый бинарный формат с версией;
- сырые датасеты не должны постоянно занимать диск;
- один и тот же анализатор используется для документов и запросов.

## Поток данных

```text
source dataset (JSONL or Parquet adapter)
      │ streaming conversion to generic JSONL
      ▼
 JSONL parser ──► Analyzer ──► batch postings (100k docs)
      │                                 │
      │                                 ▼
      └────► DocumentStore         immutable segments
                                            │
                                            ▼ k-way merge
                                    Lexicon + PostingsStore

query ──► Boolean parser ──► AST ──► lazy iterators ──► doc_id candidates
                  │                         │
                  └─► Analyzer              ▼
                                         DocumentStore ──► SERP / JSONL
```

## Компоненты и контракты

### Ingestion / `jsonl.*`

Потоково разбирает одну JSON-строку в `SourceDocument {id, title, url, text}`;
для старых корпусов также принимается имя `docid`. В памяти находится только текущая
строка. Парсер поддерживает JSON escapes и surrogate pairs. Сетевой код и декодеры
исходных контейнеров не входят в ядро: индексатор одинаково работает с файлом и
stdin. Адаптер FineWeb нужен только для чтения Parquet; построение индекса остаётся
в C++.

### Analyzer / `tokenizer.*`

Единственная точка нормализации текста. Сейчас выделяет русские, латинские и
цифровые токены, приводит регистр и отбрасывает аномально длинные токены. Позднее
сюда добавляются конфигурируемая лемматизация и синонимы. Query-time обязан
загружать ту же версию анализатора, которая записана в `metadata.txt`.

### IndexBuilder / `index_builder.*`

Индексирует ограниченный batch документов, формирует `term -> sorted doc_ids` и
сбрасывает immutable segment. Потребление RAM зависит от batch size, а не от полного
размера коллекции. После завершения выполняется k-way merge всех сегментов.

### Lexicon и PostingsStore

Словарь отображает терм в `(offset, byte_size, document_frequency)`. Postings
хранят возрастающие `doc_id` как delta+varint. Формат и инварианты описаны в
`INDEX_FORMAT.md`.

В следующей версии запись postings станет блочной: отдельные потоки `doc_id`, TF и
positions плюс skip/block metadata. Публичный контракт словаря при этом сохранится.

### DocumentStore

Хранит внешний идентификатор, заголовок, исходный URL и текст. Текст каждого
документа независимо сжат zlib, поэтому длинный веб-корпус не раздувает диск, но
любой результат можно распаковать отдельно. Массив `uint64`-смещений обеспечивает
O(1) доступ по внутреннему `doc_id`. Query worker держит `docs.bin` открытым.
Presentation layer использует только сохранённый URL (либо HTTP(S)-значение самого
внешнего ID). Ядро не угадывает источник корпуса по идентификатору или заголовку.
Legacy document store v1 по-прежнему читается, но несуществующая в нём ссылка не
синтезируется.

### SearchEngine / QueryExecutor

Загружает отсортированный словарь один раз при старте процесса и находит термы
бинарным поиском. `query_parser.*` преобразует `AND`, `OR`, `NOT` и скобки в AST.
Приоритет: `NOT` > `AND` > `OR`; неявное `AND` между соседними термами сохраняет
удобство обычного текстового запроса.

Каждый узел AST компилируется в `DocIterator` с едиными операциями `doc_id`, `next` и
`advance_to`:

- `TermIterator` лениво декодирует postings одного терма;
- `AndIterator` начинает с самого короткого списка и синхронизирует детей;
- `OrIterator` выполняет дедуплицирующий k-way merge через min-heap;
- `AndNotIterator` вычитает отрицательный поток из положительного;
- `NotIterator` нужен для общего случая, например `A OR NOT B`, и лениво перебирает дополнение.

Оптимизатор распознаёт `A AND NOT B` и не строит гигантское множество «все документы,
кроме B». Все узлы останавливаются после top-K и не материализуют полные промежуточные
списки.

CLI загружает `SearchEngine` один раз на интерактивную или batch-сессию. Batch-режим читает
одну формулу на строку, не прерывает пакет при синтаксической ошибке одной строки и выдаёт
машиночитаемый JSONL с результатами и latency-статистикой.

Сейчас порядок результатов детерминирован по `doc_id`. Точка расширения следующего
этапа — `Candidate {doc_id, lexical_features}` и ranker BM25/proximity.

### Локальный web-интерфейс

Команда `serve` один раз создаёт `SearchEngine`, затем обслуживает запросы на
`127.0.0.1`. Это принципиально отличается от запуска CLI на каждый HTTP-запрос:
лексикон и `docs.offsets` остаются загруженными, поэтому в latency поиска не входит
повторная инициализация индекса.

`GET /api/search` сначала вызывает основной `parse_boolean_query`, после чего один
и тот же `QueryNode` сериализуется для визуализации и компилируется поисковиком в
дерево `DocIterator`. Первый ответ содержит AST, страницу результатов и ID курсора.
Следующая страница продолжает тот же итератор: сервер не материализует всю выдачу,
не пишет её на диск и не повторяет поиск с `OFFSET`. В памяти хранится только
состояние максимум 32 активных курсоров; неиспользуемая сессия удаляется через 15
минут. Число страниц не ограничено, а одна HTTP-страница содержит не более 1000
документов, чтобы ограничить размер JSON и DOM.

API возвращает отдельно `search_ms` / `total_ms`. Статические HTML/CSS/JS лежат в
`web/`; внешних web-фреймворков и CDN нет. Сервер однопоточный, что достаточно для
локального демонстрационного стенда и не требует синхронизации общего файлового
потока `docs.bin`.

## Масштабирование и ресурсы

- Размер batch задаётся профилем корпуса; Learning Web использует 50 000 документов.
- Временные сегменты лежат внутри каталога индекса и удаляются после merge.
- Исходные шарды обрабатываются по одному и после конвертации удаляются.
- Лексикон и offsets загружаются в RAM один раз. Postings и тексты читаются с диска.
- Один экземпляр `SearchEngine` предназначен для одного query worker. Для
  многопоточности создаётся по reader на worker, а неизменяемый словарь позднее
  можно вынести в shared state.

## План эволюции

1. **Milestone 1:** 10+ млн полноразмерных документов, boolean retrieval,
   метрики latency/RAM/disk.
2. **Milestone 2:** positions, TF, BM25, phrase/proximity, блочная компрессия,
   evaluation dataset и Recall/MRR/nDCG.
3. **Milestone 3:** feature extraction API, L2 ranker, экспорт модели из Python в
   C++ runtime, ablation study.
4. **Final:** dense retriever, fusion, end-to-end training и демонстрационный API/UI.

## Известные риски

- FineWeb основан на публичном вебе: лицензия набора данных не заменяет права
  авторов отдельных страниц; источник и URL сохраняются.
- Отсортированный словарь пока полностью в RAM; если он станет узким местом, следующий шаг —
  sorted front-coded lexicon + sparse in-memory index или memory mapping.
- Один большой merge достаточен для текущего snapshot, но для обновляемого индекса понадобится
  tiered merge policy и атомарная публикация поколений.
- Качество текущей версии ограничено отсутствием морфологии и ранжирования; boolean
  correctness не следует выдавать за качество ранжирования.
